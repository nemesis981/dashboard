## 🚨 Critical finding — live `dashboard.service` has diverged from the repo with no fix upstream

**The repo's generator has no dashboard exception, and would re-harden dashboard (breaking it
again) on the next redeploy.**

Last night's incident recovery discovered dashboard needs to run *without* the standard
hardening block (`NoNewPrivileges=yes` etc. breaks its `sudo -n` elevation, which
`alert_manager/firewall.py` needs for the ADR-0005 ufw chokepoint — proven, not assumed, per
last night's HANDOFF). The live unit was hand-patched to remove hardening, with a comment
explaining why:

```
FragmentPath=/etc/systemd/system/dashboard.service
NoNewPrivileges=no
ProtectSystem=no
```
(confirmed via `systemctl show dashboard`, i.e. systemd's actual active configuration right
now — not a stale on-disk read.)

**But `scripts/gen_units.py` was never updated to reflect this.** Its `SERVICES` dict has a
capability exception for `device-scanner` (`CAP_NET_RAW`) but **no exception at all for
`dashboard`** — every service, including dashboard, gets the full uniform `HARDENING` block
unconditionally (`body = "\n".join(lines) + "\n" + HARDENING`, no per-service skip). The
repo-committed `alert_manager/dashboard.service` (generated by `gen_units.py`, committed in
`5e9fcc0`) still has the complete hardening block — `NoNewPrivileges=yes`, `ProtectSystem=strict`,
the full `RestrictAddressFamilies=`/`SystemCallFilter=` set, all of it.

**Consequence:** the live, hand-patched fix exists *only* on the production filesystem. It is
invisible to git, invisible to `gen_units.py --check` (which only diffs the generator's output
against the repo's own `.service` files — both of which agree with each other, just not with
what's actually deployed), and would be silently destroyed by the next legitimate-looking
deployment action — re-running `gen_units.py` for an unrelated reason, or re-running
`install.sh`, would regenerate/redeploy a fully-hardened `dashboard.service` and reproduce the
exact incident just recovered from (dashboard would start, look healthy, and be unable to block
or quarantine anything).

**This needs a code fix** (Window 1's lane, not mine): `gen_units.py` needs an explicit
dashboard exception mirroring the live hand-patch, and the corrected `dashboard.service` needs
to be committed. Until then, **do not re-run `gen_units.py` or `install.sh`'s unit deployment
step** without manually re-applying the live hardening exception afterward.

Secondary, much lower-severity divergence in the same file: the live unit also lacks
`Group=nemesis-db`, `Environment=PYTHONPATH=...`, `NEMESIS_EXPECT_USER`, `LogsDirectory=`, and
uses systemd's default `RestartSec`. None of these break anything currently (dashboard is
`active`/`running`/`NRestarts=0`), but they mean the live unit is a fuller rewrite than "just
remove hardening" — worth folding into whatever fixes `gen_units.py`, not just deleting the
hardening block from the generator's output for dashboard specifically.
