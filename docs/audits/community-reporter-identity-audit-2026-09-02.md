## 3. ⛔ THE TRAP — the install ID depends on WHO COMPUTES IT

**This is the finding most likely to cause a real defect, because it is invisible in testing.**

Two of the seven canonical signals (`system_uuid`, `board_serial`) come from
`/sys/class/dmi/id/`, mode `0400 root:root`. Measured on the production box 2026-08-17 and
documented in `install_id.py`:

    root          -> 5 signals -> one stable_id
    <user>        -> 3 signals -> a DIFFERENT stable_id
    nemesis-dash  -> 3 signals -> the same as <user>   <-- what the dashboard uses

`install_id.py` records that this **"nearly caused a real mistake"**: an id read from a root shell
did not match the id a licence had been signed against, and it looked exactly like a broken
licence. It was two different questions asked of two different processes.

**Why this is worse for a reporter ID than for a licence.** A licence mismatch fails loudly and
gets investigated. A reporter identity whose whole value is **stability over time** would instead:

- derive one id when generated by an installer running as `root`,
- derive a different id when the dashboard later recomputes or verifies it,
- and, if the derivation is ever re-run rather than read from storage, silently produce a **new
  reporter identity** — discarding accumulated trust score and submission history, which the
  document explicitly promises to preserve across migration.

**Requirement, if this is built:** the computing identity must be pinned and stated explicitly in
the design, exactly as the licence rule already is — *"a licence must be signed against the id
computed by the VERIFYING end."* The equivalent rule here needs writing down before code exists,
not after a mismatch is found in the field.

## 4. Tier-vocabulary conflict

The roadmap proposes **four** key prefixes:

    NMS-FREE / NMS-DEMO / NMS-PRO / NMS-ENT

`core/entitlements.py` defines **two** tiers:

    TIER_FREE = "free"
    TIER_COMMERCIAL = "commercial"

with a stated design principle — *"Graceful downgrade only: never hard-lock a security product
behind a paywall"* — and `FREE_TIER_REMOTE_CAP = 5`.

Shipping four key prefixes without reconciling this creates **two tier vocabularies**: the key
format says one thing, the entitlement engine another, and every consumer has to know which is
authoritative. That is the same class of problem as the two-source-of-truth patterns CLAUDE.md
already warns about for the roadmap baseline and the elevated-grants list.

**Decision needed before building:** either the four prefixes map onto the existing two tiers
(and the mapping is written down), or `entitlements.py` grows to four (and the graceful-downgrade
semantics are restated for each). Not both independently.

## 5. ⚠ FLAGGED DESIGN QUESTION — the entropy scheme and reproducibility

**Labelled as analysis of the design document, not a measurement of code. Nothing is built, so
nothing here was tested.**

The document specifies seven entropy sources combined into a salt: licence key, a randomly chosen
ping target, measured network latency, boot time, PID/TID, a nanosecond timestamp, and
`secrets.token_hex(16)`. Then:

    salt        = combine(target, latency, boot_time, pid, timestamp, random)
    reporter_id = HMAC-SHA256(license_key, salt)[:16]
    Store: reporter_id only.  Discard: licence key, latency, salt, all entropy sources.

**Two concerns worth resolving before code:**

**(a) Sources 2–6 add little once source 7 exists.** `secrets.token_hex(16)` is 128 bits from a
CSPRNG. The stated adversary model for the other sources — *"attacker doesn't know which target
was chosen"*, *"physically impossible to reproduce"* — is already defeated by that alone. What the
extra sources do add is real: an **install-time network dependency** (which the document itself
needs a documented fallback for) and additional moving parts in a security-relevant derivation.

**(b) The salt is discarded, so the result is not reproducible — which makes the stated property
questionable.** If the salt is random and thrown away, `reporter_id` cannot be re-derived from the
licence key. Functionally it is then **an opaque random identifier stored on disk**, which is a
perfectly reasonable design — but it is not what the framing claims. The document says *"The
backend can verify identity without ever seeing the key"* and *"Privacy and accountability
coexist."* With a discarded random salt, the backend cannot verify any relationship between the
reporter ID and the licence key; it can only observe that the same opaque ID keeps appearing.

**The question to settle: what provides ACCOUNTABILITY here?** If it is "the same ID keeps
appearing", the HMAC and the entropy ceremony are not doing that work and could be replaced by
`secrets.token_hex` with no loss. If it is meant to be "this ID provably belongs to a valid
licence", the derivation must be reproducible or accompanied by a proof, and the current design is
neither.

**Minor, secondary:** `[:16]` is 16 hex chars = **64 bits**. Fine at realistic install counts
(birthday collisions near 2^32), but worth stating as a deliberate choice rather than leaving it
implicit.

## 6. Summary — what has to be decided before this is buildable

1. **Derive from `install_id.py` or not?** Its header says no new fingerprinting code; the
   roadmap specifies new fingerprinting code. One of the two has to give.
2. **Pin the computing identity** (§3) — the near-miss is already on record; the equivalent rule
   for reporter identity does not exist yet.
3. **Reconcile the tier vocabularies** (§4) — four prefixes or two tiers, with an explicit mapping.
4. **Settle what accountability means** (§5) — which then determines whether the entropy ceremony
   is load-bearing or removable.
5. **Confirm which of the seven dependents actually block on this**, since that is the stated
   reason for prioritising it.

**None of these is a code problem.** They are all design decisions, which is why this audit stops
here rather than proposing an implementation.
