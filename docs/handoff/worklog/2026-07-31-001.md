## Read-only investigation — `quarantines` table discrepancy (HANDOFF §1/§3/§5)

Flagged in HANDOFF as: a `fw_block_ip` by `alert-watcher` against the test VM's tailnet
address (07-30 11:05) with no corresponding `quarantines` row; "worth a two-minute look
before assuming the dashboard's quarantine list reflects it correctly."

Read-only throughout (Rule 1). No state changed.

### Findings, in order

1. `quarantines` is empty — **0 rows across all statuses**, not merely 0 active.
2. No production code deletes from it. Expiry does `UPDATE ... status='expired'`
   (`alert_watcher.py:318`); only `alert_manager/test_quarantine.py:103` deletes, and only
   its own rows by `rule_id`. Rows should therefore accumulate, not vanish.
3. Not a split-DB problem. `nemesis_paths.db_path()` resolution is consistent, and all nine
   systemd units pin `Environment=NEMESIS_DB_PATH=/var/lib/nemesis/alerts.db`.
4. Stray DB copies exist at `/opt/nemesis/alerts.db` and
   `<user-home>/dashboard/alert_manager/alerts.db` — both **0 bytes, no schema**, harmless
   leftovers. `*.db` is gitignored (`.gitignore:5`), so no Rule-8 exposure from the in-tree one.
5. **The 07-29 backup also has 0 quarantine rows**, with 46 audit rows including two
   `fw_block_ip` entries from 07-28. So rows were never wiped — they have **never landed**.
6. **Root cause.** No alert has ever carried `action='auto-quarantine'` (only
   `acknowledged` 4 / `ignore` 4 / `pending` 9). `alert_watcher.process_new_alert()`'s
   auto-quarantine branch — the only path that calls `insert_quarantine_row()` — has never
   fired in production. Every `fw_block_ip` in `audit_log` instead arrived via
   `nemesis_fwd`'s direct `block_ip` op, which writes an audit record but deliberately
   writes a quarantine row **only** for `peer_name == "fail2ban"`
   (`nemesis_fwd.py:808-812`, landed `eb1943c` on 07-30 — after the 07-29 fail2ban test,
   which is why that test left no rows either).

### Verdict
**Not a bug. The HANDOFF discrepancy dissolves.** The missing row for the test VM address is
correct behaviour: that block did not come through the auto-quarantine path. The dashboard's
quarantine list is accurate — it is empty because nothing has ever been auto-quarantined.

### Method note
First attempt at checking open fds used `sudo ls -l /proc/<pid>/fd` and `sudo find /`. There
is no NOPASSWD grant for either, so both **silently returned nothing** and read as
"no alerts.db open anywhere" — a false finding. Caught by noticing `find` failed to report a
file already known to exist. Re-ran without `sudo`. Same shape as the five misreads logged in
`2026-07-30-002.md` §7; the rule that catches it ("run the command that would disprove it")
worked here.

### Captured, not fixed (Rule 7 — small fix, for PUNCHLIST)
`audit_log.rule_id` is overloaded. `dashboard.py:996` writes a genuine alert `rule_id`;
`nemesis_fwd.py:523` writes a **`request_id`** into the same column (`detail=req.get("request_id")`).

## Defect 1 — FIXED AND LIVE (never-block guard at the chokepoint)

Placed in `firewall.py`, the ADR-0005 chokepoint, NOT in the dashboard caller. The guard
previously existed only as `alert_watcher._blockable()`, protecting the AUTOMATED path while
the human-triggered one was unguarded. At the chokepoint every caller inherits it, including
callers that do not exist yet. Applied to `ufw_insert_top()` and `ufw_deny_append()` only —
**deliberately NOT** to `ufw_delete`/`expire_quarantine`: refusing to REMOVE a rule on a
protected address would block the exact repair someone would need.

**Protection is RUNTIME-DERIVED, not configured.** `never_block_set()` = loopback
(unconditional) ∪ every address on the live interface list (via `psutil`) ∪
`NEMESIS_NEVER_BLOCK`. Deriving the host's own addresses at runtime means it cannot be
forgotten at install time, cannot go stale when DHCP moves the LAN address, and covers the
tailnet address with nobody naming it. Config that must be remembered is config that gets
missed — proven twice today (see Defect 2 below). `psutil` failure degrades to
loopback + env only, logged, never silent.

Verified by direct test before deploying — **13 addresses protected**, all 3 local v4
addresses included:

| Address | Result |
|---|---|
| `127.0.0.1` | REFUSE |
| host LAN address | REFUSE |
| `203.0.113.77` | ALLOW |
| `8.8.8.8` | ALLOW |

Refusal raises `FirewallDenied(kind="never_block")`, logged at ERROR; dashboard maps the new
kind to HTTP 400. Dashboard + alert-watcher restarted clean, zero warnings.
Note `alert_watcher._blockable()` is now redundant but retained — defence in depth, and it
records its own "alert recorded as pending" behaviour.

## Commit 2 — `write_env` + `restart_dashboard` in nemesis-fwd. DONE, not yet wired.

**`write_env`** — takes `{key: value}` pairs, never a file body. Validation is helper-side
because the caller is modelled as compromised, so a check the caller performs is a check an
attacker skips:
- key must match `^[A-Z][A-Z0-9_]*$`
- **denylist checked FIRST** (`PATH`, `LD_PRELOAD`, `LD_LIBRARY_PATH`, `LD_AUDIT`,
  `PYTHONPATH`, `PYTHONSTARTUP`, `BASH_ENV`, `IFS`) so it holds even if the allowlist is ever
  wrong
- then the 10-key allowlist, citing `dashboard.py:4547` as authoritative
- value must be a string, ≤2048 bytes, and contain no `\n`/`\r`/NUL — the newline check is
  the load-bearing one: a newline injects a SECOND assignment, which is how an allowlisted
  key becomes a way to set a denied one
- helper does the whole read-merge-write; atomic via temp file in the same directory with
  mode/ownership set BEFORE `os.replace()`, so a torn or briefly world-readable
  `/etc/nemesis.env` (16 secrets) never exists on disk

**`restart_dashboard`** — no parameters at all. `systemctl restart --no-block`, because the
caller IS the dashboard: a blocking restart would stop the process waiting on the socket
before it could read the reply.

Audit names `svc_write_env` / `svc_restart_dashboard` — not `fw_*`, per commit 1.

### Verified before deploying
**15 validation cases, all correct** — allowlisted accept; non-allowlisted, `LD_PRELOAD`,
`PATH`, newline injection, CR injection, NUL, lowercase key, shell-metachar key, non-string
value, oversized value, empty payload, non-dict values, missing values all rejected.

**Merge tested against a scratch copy, never the live file** (only `os.chown` stubbed, since
it needs root): comments and section headers preserved, existing key updated in place, old
value gone, new key appended, untouched secrets intact, no duplicate keys, resulting mode
`0640`. Live `/etc/nemesis.env` confirmed untouched (mtime still 2026-07-01).

**Registration verified by executing the module:** both ops in `OPS`, both in `WRITE_OPS` (so

`unattended peers granted the new ops? False`. That matters: `alert-watcher` and `fail2ban`

## Wizard fix — send only EDITED fields (the NETWORK_IFACE side effect)

`_wizCollectChanges()` now records a field only when `el.value !== el.defaultValue`.

**Why `defaultValue` and not a comparison against stored config** — this is the crux, not a
style choice. `defaultValue` is the value the input was RENDERED with. `NETWORK_IFACE` renders
from live auto-detection, NOT from the stored value, so comparing against stored config would
still mark it changed whenever detection disagreed — exactly the observed failure, where two
saves touching only `SMTP_HOST` silently rewrote `NETWORK_IFACE` to the VPN interface.
Comparing against what was on screen is what actually fixes it. Secret fields render empty, so
typing anything counts as a change (correct — nothing on screen to compare against), and a
blank field still never clears a stored value.

`py_compile` + `node --check` clean on the rewritten function.

**Deployment trap caught before it misled a test:** dashboard.py was edited at 14:38 while the
service had been running since 14:30:42, so the process was still serving the OLD wizard.
Test 2 would have exercised unfixed code and looked like the fix failed. Verified by comparing
process start time against file mtime — not assumed — then restarted. Worth remembering: an
edit is not a deployment, and "I just changed it" is not evidence the change is running.

## QUEUED FEATURE (operator, 2026-07-31) — idle-lock / walk-away protection

**Not designed. Not started. Captured per Rule 7 so it is not lost.**

Lock the dashboard session after X minutes of inactivity, requiring the password before it is
usable again.

**Purpose distinction the operator drew explicitly, worth preserving:** this is *preventive* —
no live authenticated session sits open unattended. It is NOT the same as the `login_events`
centralisation, which is *forensic* — who tried and failed. One removes the opportunity, the
other records the attempt. Both are wanted; they are not substitutes.

Stated requirements:
- client-side inactivity timer
- server-side session expiry (the client timer alone is not a control — a hostile or
  non-cooperating client simply does not fire it, the same limitation already documented on
  the credential-cache drop path)
- re-auth flow that does **not lose unsaved work in progress**
- configurable timeout with a sensible default

Sequencing agreed: **login_events centralisation first, idle-lock after.**
