## Idle-lock / walk-away protection — design

- Investigated current session handling: no idle tracking exists today, Flask-Login sessions
  never expire until browser close/logout; `_enforce_setup_and_auth()` is the existing
  chokepoint (already used for the password-expiry confine-don't-reject pattern); `session[...]`
  already holds ephemeral per-session state (`pw_recovery_at`), so `last_activity` can live in
  the signed cookie with no schema change; `_register_credential_failure()` is a shared
  brute-force budget across login/change-password that a new unlock endpoint must reuse.
  Central risk found: the dashboard's existing background auto-polling
  (`setInterval(refreshDashboard, 60000)` etc.) would silently defeat a naive
  "any request = activity" design.
- Proposed design + six-step implementation sequence, written to
  `docs/roadmap/idle-lock-walk-away-protection.md`. Reported to operator before any code.
- Operator approved 2026-08-01: 15-min default, no disable switch in v1, `audit_log` row on
  lock transition (once per lock event, dedup via a session flag).
- Rule 10 flag: the design's "unsaved work" section named a specific fallback-path gap
  (server-side redirect can lose in-progress form state in the case where the client-side
  overlay doesn't fire in time). Operator decision: extract to
  `~/work/nemesis-internal/known-limitations/idle-lock-unsaved-work-gap-2026-08-01.md` in
