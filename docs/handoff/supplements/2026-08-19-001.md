## Two real bugs caught by verification before they shipped

Both found by this window's own pre-commit verification, neither assumed
away, neither fixed by editing code content directly (both sent back to
Window 1):

1. **`dashboard.py` use-after-close (`d3f1892`).** The mandatory
   route-security audit — run per standing practice regardless of Window 1's
   own "doesn't trigger" assessment, per explicit operator instruction not to
   skip it — found `get_network_devices()` closing its DB connection *before*
   calling `hw_monitor.approved_agent_macs(conn)` on it. That function's own
   `except Exception: return set()` (no logging) silently swallowed the
   resulting `ProgrammingError` on every call, making `has_agent`
   unconditionally `False` for every device — the entire ADR 0023 correlation
   feature dead on arrival, invisibly. Window 1 fixed both the ordering and
   the root cause (the function now logs at ERROR on any read failure).
   Re-ran the *full* audit on the fixed file (not just the one bug, per
   explicit instruction), and independently re-verified beyond the new unit
   test by extracting and live-executing the real `get_network_devices()`
   against a throwaway DB.
2. **`mem_appliance.py` missing `import time` (`fd67bcc`).** `throttle_status_report()`
   called `time.time()` with no `import time` anywhere in the file — a
   guaranteed `NameError` on every real call to the new `/api/throttle-status`
   route, since no caller passes `now=` explicitly. Reproduced live in
   isolation before reporting it. No dedicated test existed for the new
   function (the prior tests only covered the earlier static classification),
   which is why it wasn't caught before landing. Window 1 fixed it and added
   `test_throttle_status_report_and_log_line`, which exercises the exact
   default-`now=None` path directly.

## Process incident: an accidental live-DB write, corrected

While verifying the (then still-held) Tier 2 schema migration in isolation,
a verification script called `modules.set_shared_db_path(<tmp path>)` before
importing `hw_monitor`, intending to sandbox `init_db()`. It didn't work —
`hw_monitor.py`'s own `DB_PATH` resolves independently via
`nemesis_paths.db_path()`, which checks the relocated production path
(`/var/lib/nemesis/alerts.db`) first and used it because it exists on this
box. `init_db()` ran directly against the live production database, adding
three columns (`tier2_state`/`tier2_detail`/`tier2_at`) to `agent_devices`
via the code's own guarded, additive migration — before the commit shipping
that migration had even landed.

Reported to the operator immediately and in full, before any further action.
Outcome verified benign (integrity_check ok, row counts unchanged, no data
touched — and the same migration the held commit would have applied on next
restart regardless), but the *process* gap was real: no State Snapshot taken
first, no pause for go-ahead. Operator accepted the outcome and directed
three things, all done: an after-the-fact State Snapshot
(`nemesis-state-backups/2026-08-19-1451-after-the-fact-tier2-schema-migration/`),
a PUNCHLIST entry naming the root cause (two DB-path mechanisms in this
codebase don't compose — redirecting one doesn't redirect the other), and a
corrected verification approach for the rest of the session (explicit
`NEMESIS_DB_PATH`, confirmed honored before trusting it, for every
subsequent test that touches a real init/migration function). Committed as
`c44278a`.

## Tonight's closeout finding: a real, live, currently-harmless gap

Gathering facts for tonight's closeout (service restart timestamps, to
determine what's actually live vs. just committed) surfaced something not
just a status fact: `hw-monitor`, `dashboard`, `watchdog`, `alert-watcher`,
and `diagnostics-watcher` had all been restarted this evening by someone
other than this window (this session never ran `systemctl restart` on
anything). `hw-monitor` restarted at 18:34:58, after `059da4b` (16:24:50,
the production-ladder-loop commit) — meaning **the memory-injection ladder
loop is now genuinely live**, not just committed. Verified this directly
rather than inferring it from timestamps alone: `mem_ladder_state.sample_seq`
is at 23 and incrementing on the expected ~5-minute cadence.

That verification step surfaced a real gap: `mem_ladder_state`,
`mem_shadow_records`, and `agent_attestation_challenges` (all three new
tables from `059da4b`) were never added to `hw_monitor`'s Data Manager
namespace grant in `alert_manager/data_manager.py`. Confirmed via
`journalctl -u hw-monitor`: `mem_ladder_state` writes are hitting `WOULD
DENY (warn-only)` on every ladder cycle since the restart. This is currently
harmless — DataManager write enforcement is still WARN-only, so the write
goes through anyway, and `run_ladder_cycle`'s own try/except means even a
real DENY would degrade to "no ladder this tick" rather than crash the
service — but it is exactly the failure shape the `agent_device_macs`
grant's own comment in the same file warns about, and it MUST be fixed
before DataManager enforcement is ever flipped to `MODE_ENFORCE`, or both
the ladder loop and Tier 2 issuance go silently dark at that moment. Not a
Window 2 fix (code content); filed as a PUNCHLIST entry with full citation
and a candidate fix (add the three table names, plus a direct grant-assertion
test matching the `agent_device_macs` precedent) for Window 1 to pick up.

`dashboard` also restarted, at 20:25:15 — after `368b828` (RAM recovery,
19:54:25) — so that feature is live too.
