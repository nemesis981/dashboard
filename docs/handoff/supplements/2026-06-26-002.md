## 3. Scan / task orchestration — direction decided (ADR 0004, Proposed)

**Decision direction:** a dedicated **scheduler module** becomes the *authoritative dispatcher*
for all scan/task dispatch (what runs, when, against which target); **execution modules**
(malware = the full-stack engine; hardware; future) do the work; a separate **reporting module**
processes results and delivers printable reports in the dashboard. **`hw_monitor` is reduced to
hardware-only.**

**North-star driving it:** the product thesis — *affordable self-hosted zero-day/behavioral
detection + whole-network security; enterprise capability without enterprise pricing.* The
architecture must enable **automated, fleet-wide, FULL-STACK detection, because that IS the
product.** Today full-stack runs only on a manual button on one host — the gap this closes.

**Evidence base — the audit's 6 cross-cutting facts** (`docs/audits/scan-task-architecture-audit.md`):
1. No single scan path (3 local scanners, 2 engine sets, 2 table families).
2. YARA + heuristics reachable only via one manual button.
3. All automation/fleet/condition scans are **clamav-only**.
4. Scheduled scans are **DEAD** — `scan_schedules` write-only, no timer/worker drains the queue;
   dispatch is purely event-driven on agent check-in.
5. Scan dispatch is **welded into the `hw_monitor` `/hw_data` handler** (interleaved with
   hardware ingest + device-state mgmt).
6. All five `scan_*` tables are **core/unprefixed**; remote HW monitoring is **BUILT** but remote
   full-stack scanning is **NOT** (agent is clamav-only).

**3 open hinge questions** (recorded in ADR 0004, deliberately not answered yet): (a) one unified
findings table vs two (`scan_jobs`/`scan_threats` vs `malware_findings`); (b) how full-stack
reaches the fleet (ship engine code to endpoints vs ship files back); (c) where the five `scan_*`
tables migrate (scheduler-owned `scan_*` vs fold into `malware_*`).

## 8. Pass 0 Stage 4 — CLOSED (Pass 0 fully complete)

The two remaining duplicate-`CREATE` collapses are done; **Pass 0 is now complete end to end.**
Both were driven by the same Stage-4 audit, but resolved **oppositely** — a deliberate outcome of
audit-first, because the safe move depended on facts a blind delete would have missed.

- **`hw_alerts` — deleted the redundant CREATE (commit `f19e5c5`).** Two near-identical CREATEs:
  `hw_monitor.init_db()` and `watchdog._init_cooldown_table()`. **watchdog is the sole writer and
  the natural owner**; `hw_monitor` only *reads* the table, via the **exception-guarded
  `get_hw_alerts()`** (`except: rows=[]`). With **no systemd ordering** between the services,
  deleting the *reader's* CREATE is safe — a read that races ahead of creation degrades to empty,
  never crashes. Kept watchdog's CREATE; removed hw_monitor's. Live table untouched.
- **`quarantines` — extracted to ONE shared init, kept BOTH call sites (commit `fb7e7fc`).** Here
  the audit said *do not delete either side*: the dashboard's read path (`get_active_quarantines`)
  does an **UNguarded SELECT**, and again there's **no startup ordering** — so removing either CREATE
  reintroduces a missing-table crash. The real hazard of duplicate DDL is *drift*, and the fix for
  drift is a **single source of truth**, not removing a call site. Added canonical
  `init_quarantines_table()` to `alert_manager/database.py` (the core schema module **both**
  processes already import — `alert_watcher` deliberately does *not* pull in the `modules`/`get_db`
  layer, and `quarantines` is a core unprefixed table, so `database.py` is the correct home, not the
  module accessor). Both call sites remain as thin wrappers: `alert_watcher.init_quarantines_db()`
  (startup, create-before-write) and `dashboard._ensure_quarantines_table()` (lazy self-heal before
  the unguarded SELECT). **One DDL definition, two callers — dedup the text, keep both safety nets.**

*Lesson reinforced:* two superficially identical duplicates can have opposite safe resolutions; the
discriminators were (a) reader exception-guarded or not, and (b) absence of startup ordering. This is
exactly why Stage 4 was audit-first per Rule 1.

## 10. Design captures (PARKED — ADR/roadmap-bound, NOT built this session)

Captured per Rule 7 (write down with reasoning, don't chase mid-task). None implemented; each lands
as an ADR, roadmap stub, or CLAUDE.md principle.

- **Namespace reservations as anti-drift markers** (roadmap/ADR-0004-adjacent). Reserve
  `modules/scheduler/` and `modules/reporting/` *now* — each just a `README` saying *"this concern
  lives here; don't scatter it; see ADR 0004."* **Why:** scheduling logic already drifted into 4+
  places (the Stage-4 audit fact that scan dispatch is welded into `hw_monitor`'s `/hw_data` handler
  is the same disease); a reserved namespace is a cheap global-awareness marker that prevents
  recurrence before the module is built.
- **Schema gatekeeper / registry** (ADR-bound — open-source contributor safety). Modules **declare**
  their schema; **core creates all tables before any module logic runs** (option B1 — *prevent by
  contract*, the structural generalization of what we just did by hand for `quarantines`). Plus a
  **resilience layer**: missing table → bounded retry → structured-error log → **graceful module
  UNLOAD into a disabled state with a visible reason** (never a silent crash). The gatekeeper is
  **MANDATORY and unbypassable** (*no gatekeeper, no load*) and the **SOLE DB-access path** — which
  makes ADR 0001's *write-own / read-scoped* rule **structurally enforced, not convention**. This is
  the durable answer to "every cutover this session had to grep all cross-process callers by hand."
- **Third-party module TRUST & ISOLATION model** (SEPARATE ADR). The DB-gatekeeper is
  **necessary-but-not-sufficient**: a hostile/sloppy module can bring its **own** DB, flat file,
  network socket, or subprocess, and the DB gate won't stop it. Layered answer: **curation/review
  (trust) now**, + **capability declaration in the manifest (transparency)**, + **process/privilege
  isolation (enforcement) later**. **Honest caveat recorded:** real Python sandboxing is hard;
  near-term posture is *curation + transparency*, NOT technical enforcement — don't oversell it.
- **Ownership / consent boundary** (PRINCIPLE — CLAUDE.md-bound). Device-action capabilities are
  **gated by ownership context**:
  - **Owned / agent-bearing devices** → scan / inventory / log-fetch permitted **with consent**.
  - **Venue / unowned devices** → **network-behavior observation ONLY**; never force-scanned or
    log-pulled.
  - **Agent presence = consent signal** sufficient for the **low** tier. The **sensitive** tier
    needs **agent presence + explicit attributed "type-YES" authorization** from an **owner/admin**
    + a **recorded attribution of who authorized it** (ties straight into the multi-user-ready
    `actor`/attribution seam and the §5 key-unlock model).
