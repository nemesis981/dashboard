## 2. VPN / DNS — REFRAME: the issue is NOT resolved

**Supersedes the earlier conclusion** ("PIA client bug, reboot fixed it"). It is **intermittent**:
this session it worked ~1 hour with PIA on, then connectivity dropped — Code lost its
`api.anthropic.com` link and re-login failed while fetching the auth key. A reboot masking it
once was misleading; the failure recurs. (Note this is the *trigger/symptom* layer; ADR 0002
still pins the underlying DNS design on PIA's killswitch + policy routing.)

**Action: built a read-only watcher** at `~/work/vpn-watcher/vpn-watch.sh` (OUTSIDE the repo —
it logs real LAN/tunnel IPs; never committed). It observes only, changes nothing, loops every 3s
appending to a dated logfile (flushed per write so data survives the outage): PIA state, tunnel
iface, default route + full `ip rule` + `ip route show table all`, the kernel's chosen source IP
(`ip route get`), DNS resolution + resolver, raw egress by IP, and — the key test — the
`api.anthropic.com` auth path, split into **default / `-4` / `-6`** variants.

**Key leads surfaced during the build (PIA was off at the time):**
- PIA leaves a **`blackhole default` in table `piavpnOnlyrt`** even when *disconnected*, plus
  its `ip rule` entries (100/101/102 → piavpn tables) persist. Residual killswitch routing is a
  prime suspect for the outage.
- `api.anthropic.com` **resolves to IPv6** — so the outage may be **v6-routing-specific** (hence
  the v4/v6 split in the auth test).

**Next session:** when the next failure hits, read the log around that timestamp — compare the
v4 vs v6 KEYTEST results and the source-IP/route state to pin the mechanism.

## 3. Scan / task orchestration — direction decided (ADR 0004, Proposed)

**Decision direction:** a dedicated **scheduler module** becomes the *authoritative dispatcher*
for all scan/task dispatch (what runs, when, against which target); **execution modules**
(malware = the full-stack engine; hardware; future) do the work; a separate **reporting module**
processes results and delivers printable reports in the dashboard. **`hw_monitor` is reduced to
hardware-only.**

**North-star driving it:** the product thesis — *affordable self-hosted zero-day/behavioral
detection + whole-network security; enterprise capability without enterprise pricing.* The
architecture must enable **automated, fleet-wide, FULL-STACK detection, because that IS the
product.** Today full-stack runs only on a manual button on one host — the gap this closes.

**Evidence base — the audit's 6 cross-cutting facts** (`docs/audits/scan-task-architecture-audit.md`):
1. No single scan path (3 local scanners, 2 engine sets, 2 table families).
2. YARA + heuristics reachable only via one manual button.
3. All automation/fleet/condition scans are **clamav-only**.
4. Scheduled scans are **DEAD** — `scan_schedules` write-only, no timer/worker drains the queue;
   dispatch is purely event-driven on agent check-in.
5. Scan dispatch is **welded into the `hw_monitor` `/hw_data` handler** (interleaved with
   hardware ingest + device-state mgmt).
6. All five `scan_*` tables are **core/unprefixed**; remote HW monitoring is **BUILT** but remote
   full-stack scanning is **NOT** (agent is clamav-only).

**3 open hinge questions** (recorded in ADR 0004, deliberately not answered yet): (a) one unified
findings table vs two (`scan_jobs`/`scan_threats` vs `malware_findings`); (b) how full-stack
reaches the fleet (ship engine code to endpoints vs ship files back); (c) where the five `scan_*`
tables migrate (scheduler-owned `scan_*` vs fold into `malware_*`).

## 4. Reporting module — UX intent

A dashboard **button that flashes on a new report**, with **per-user unread state** (multi-user-ready
from day one — not a global flag). Click → reports page → preview / print. Captured now so the
reporting module is built with attribution-shaped state from the start.

## 5. Licensing principle (NEW — flag for CLAUDE.md promotion next session)

**SINGLE version of the product; a key/license system unlocks commercial features**
(multi-user, attribution, device limits) **IN PLACE — not a separate fork or build.** This is the
*"why"* behind the existing multi-user-ready / "leave the socket, don't wire the house"
discipline: **the key is what wires the house.** Every multi-user-ready seam we leave (actor
fields, per-user state, single update paths) exists so the license key can light it up without a
rewrite. → Promote to a CLAUDE.md Tier-2 principle next session.

## 6. VPN self-diagnostic — feature idea (the watcher's product future)

Generalize the throwaway PIA watcher into a **toggleable connectivity self-diagnostic** feature
(any VPN provider, not just PIA). When connectivity breaks, it captures the state (as the watcher
does now), **AI-evaluates it into a plain-language diagnosis**, and delivers **either**: an on-site
gated fix suggestion, **or** an auto-generated **complete support ticket** (captured state +
diagnosis + matched past incidents) so support starts informed instead of from zero.

**Guardrail (non-negotiable):** actual config edits go through the **Teaching / Automated approval
gates — NEVER silent auto-apply of safety-critical network config.** This mirrors the existing call
that *AI firewall troubleshooting is manual/teaching, not automated* — same consistent guardrail.
**Build AFTER the PIA root-cause fix** (don't productize a diagnostic for a bug we haven't
characterized yet).
