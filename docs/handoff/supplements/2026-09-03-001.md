## Push-coordination discipline — the day's dominant theme

Nearly every push this session hit the "unpushed set changed since confirmation" gate — a
genuinely busy shared tree with Windows 1 and 3 both actively committing. **Every single time,
the gate caught something**: a new commit landed between confirmation and push, or a set the
operator named turned out to be a subset or superset of what was actually unpushed. Handled
uniformly: re-list fresh, name what changed, push the exact confirmed SHA rather than the
branch tip, verify the remote landed exactly where intended. Zero commits were published that
weren't explicitly confirmed; zero confirmed commits were left stranded past their confirmation
by a stale push.

One case went the other direction — Window 1 relayed (secondhand, from the operator) that two
commits belonged to Window 3; I held both and messaged the two idle peer sessions directly for
first-party confirmation rather than act on the relay. Window 1 (`nemesis-1f`) confirmed the
commits weren't theirs and flagged that my own re-listing was itself stale (one of the two was
already pushed). Window 3 (`nemesis-f0`) then confirmed ownership first-party and independently
caught the same staleness. Everything was cross-checked against live git state (`merge-base
--is-ancestor`, fresh `git log` ranges) rather than trusted from any single account, including
my own prior turns.
