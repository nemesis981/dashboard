## INCIDENT — `ed6af88` orphaned commit (open, unresolved as of this closeout)

**What happened.** While landing Window 1's email-enrollment change (meant to be a 4-file
commit: `dashboard.py` + `roles.py` + `views.py` + `writes.py`, plus matching `database.py`
edits), I committed `dashboard.py` alone as `ed6af88`. Immediately after, a reset command I
ran — intended to reset a scratch directory — carried a stray `-C /opt/nemesis` and used
bare `checkout -- .`, so it executed against the real repository instead and discarded every
unstaged tracked-file change tree-wide. This wiped the three companion files plus unrelated
in-flight work (`attestation.py`'s CHALLENGE_TTL fix, three doc corrections). `2>/dev/null;
true` on the command suppressed any error signal. Net result: `ed6af88` landed in history
referencing functions that existed nowhere else in the committed tree, and `main` went red.

**Operator caught this and issued a stop on further destructive git operations.** I gave a
full account when asked, confirmed via reflog/stash (no reset, empty stash — consistent with
a direct working-tree checkout rather than a lost commit), and took no remediation action
pending instruction.

**End-of-day status (this session, all read-only verification):**

- `HEAD == origin/main == 36c3101`, unchanged since last night. `36c3101` (file-integrity
  manifest) sits two commits above `ed6af88` — the orphaned commit is not recent-tip-only, it
  is buried under later, unrelated, legitimate work.
- **The defect is still live in committed history.** An isolated `git worktree` checkout of
  `HEAD` alone (no working-tree contamination) runs `test_roles.py` at **156 passed, 2
  failed** — both failures because `roles.py` at HEAD has no entries for the enrollment
  routes `dashboard.py` at HEAD registers. A deploy or fresh clone from `origin/main` today
  would reproduce the exact break the operator found.
- **The working tree has been repopulated, but this is not a clean restoration.** Other
  windows have continued work in the same files since the incident. `git status` shows the
  wiped files back as modified, PLUS newly-untracked files that did not exist at the time of
  the incident (`modules/email_security/enrollment.py`, `baseline.py`, `sender_id.py`, three
  new email_security tests, `alert_manager/integrity_watch.py` + two new tests) — forward
  progress from other windows, layered on top of the recovery, none of it reviewed or handed
  off to me.
- A `test_roles.py` run against the (non-isolated) working tree shows 158/0 passed — this
  reflects the uncommitted state, not committed history, and should not be mistaken for the
  incident being resolved. Recording this distinction explicitly since collapsing the two is
  the exact "measured the wrong thing and it looked plausible" shape CLAUDE.md's SHAPE-check
  practice exists to catch.

**Deliberately not actioned.** I have not committed anything to close `ed6af88` out. Two
reasons: the operator's standing instruction to stop destructive git operations pending a
clear account (given, above), and the fact that the working tree now mixes the wiped-and-
restored companion files with new unreviewed work from other windows in the same files —
committing now risks repeating the exact "bundle things that shouldn't be bundled" failure
that caused the original incident. This needs an explicit operator call: whether to have
Window 1/3 hand off the restored companions as a clean, reviewed batch (closing `ed6af88`
properly), or some other remedy.

## Process note

No change to standing practice is proposed here beyond what CLAUDE.md already states — this
was exactly the "shared-index / shared-tree" and "verify the SHAPE not just the value" hazard
classes already documented, hitting Window 2 (the git-writer) rather than a build window.
Worth flagging for whoever next edits the shared-discipline section: the existing rules cover
"don't stage by bare path" and "don't stash" — a bare `-C <repo> checkout -- .` run from the
wrong cwd is a third, structurally identical hazard (a command scoped by flag rather than by
cwd, executed with the wrong assumption about which one was live) that isn't named yet.
Flagging, not adding — a CLAUDE.md edit is a docs decision, not mine to make unilaterally in
the middle of an incident writeup.
