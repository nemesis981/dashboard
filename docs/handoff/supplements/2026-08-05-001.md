## The chat-widget rescue arc

Three real, sequential defects hid behind the single symptom "chat looks broken," found and
fixed one at a time as each fix revealed the next:

1. **Duplicate `id="nemChatSection"`** (`dd32ccb`) — three surfaces each embedded their own
   copy of the widget markup onto the same page. `getElementById` returned whichever copy
   loaded first, so the alert modal's chat toggled a node nested inside
   `anomaly_detection`'s `display:none` overlay — invisible, no error anywhere. Fixed via
   render-once/relocate-everywhere.
2. **This did NOT restore chat.** The actual cause, found next: three literal newlines
   inside a single-quoted JS string (the tier-switch confirm dialog) produced a silent
   `SyntaxError` in the generated JavaScript, killing the entire chat IIFE —
   `nemChatAttach`/`nemChatInit`/`nemChatClose` were never defined on any page (`a5c7137`).
   Matches CLAUDE.md's documented #1 recurring bug class exactly. Verified independently
   by re-rendering the actual `get_chat_js()` output and running `node --check` on it — not
   just trusting the claim, since this exact function had just had a JS-syntax scare.
3. **A third, smaller defect**, found once the first two let real requests through:
   `_anchor_load_alert()`'s connections never set `sqlite3.Row`, so every `r['col']` access
   would have raised (`940b1a6`).

Once chat actually worked, two features landed on top: copyable answers with fenced-code
extraction and per-block copy buttons (`746d522`), and Enter-to-submit with Shift+Enter
still inserting a newline, gated on the Ask button's own disabled state so it can't
double-spend a turn (`2129331`).

## The analyze-alert chain — the same shape, a second time

1. **Off-by-one indices.** `analyze_alert()`'s `SELECT *` mapping was one index short on
   two DISPLAY reads (`existing[4]`/`[5]` instead of `[5]`/`[6]`) — fixed free, since it was
   pure display. The SAME off-by-one was also in the early-return GATE itself
   (`if existing and existing[4]:`), deliberately left wrong pending a cost decision:
   correcting it would start making real billed AI calls for every alert that currently
   returned instantly. Cost was measured (~$0.08–0.16 one-time against 20 un-analysed
   alerts) and the operator approved the fix same day (`9521346`).
2. **Empty deep-linked body.** The moment the gate started working, the first deep-linked
   analysis asked the model to analyse an empty string (the deep-link entry point has
   ALWAYS passed `raw=""`). The model correctly said "no data provided" — and that
   non-answer was billed, cached for 24h, and written back to `alerts.explanation`, where
   the now-correct gate early-returns on it PERMANENTLY. Measured live: alert `1000002`'s
   `risk_level` went CRITICAL → LOW on a rule seen 108 times. Fixed by rebuilding a real
   body from the stored DB row when `raw` is empty, and refusing with 422 before calling
   the AI at all when neither source has anything (`8f227a4`).
3. **Fenced JSON.** The very next real call surfaced a THIRD defect: the model's (correct,
   MEDIUM) reply came back wrapped in a ` ```json ` fence, `json.loads()` died on the first
   backtick, and the fallback hardcoded `risk_level="UNKNOWN"` straight over the stored
   CRITICAL — the analysis was right, only the storage was wrong. Fixed with a
   fence-tolerant parser returning an explicit `None` sentinel (never a fake empty dict),
   and `COALESCE(?, risk_level)` on the write-back so a parse failure can never again
   overwrite a real severity (`f8c116f`).

Alert `1000002` went CRITICAL → UNKNOWN → LOW → (repaired) → MEDIUM over the course of this
chain. Confirmed live in the closeout check: it now reads MEDIUM with a real, readable
explanation.

## ADR 0019 Phase 2 — landed as a coupled pair, deliberately

`degraded_ingest.write_offset()` was stamping SQLite's `datetime('now')` — UTC — while every
other timestamp in the database is local (the same class of bug already documented and
fixed once before in `alert_manager/database.py`). Nothing had broken, because nothing had
read the column yet. The new enforcement-visibility panel is the first reader, and would
have compared a UTC stamp against a local `now` and reported a healthy 60-second sweep as
five hours stale, permanently. Landed in one commit (`31a9bbf`) specifically so the panel
never shipped in that broken intermediate state on any host.

The panel itself self-caught a bug during its own build: a sweep stamped in the future
(exactly what the pre-fix UTC stamp produced — measured `age = -17957s` live) satisfied
`age <= threshold` and read as HEALTHY — the most confident possible answer from the most
broken possible input. Fixed with a lower bound on age, tested with a control proving 2s of
ordinary clock jitter still reads healthy.

## Two working-tree accidents caught mid-session — both self-caught, both fixed before push

1. **A splice-technique bug, twice.** Several PUNCHLIST commits this session needed
   isolating one new entry from other windows' concurrent, uncommitted WIP in the same
   file. The technique (reconstruct HEAD + new entry, stage it, restore the fuller working
   file) has a failure mode: if the "restore" snapshot is taken BEFORE the new entry is
   written, restoring it silently drops the entry from the working tree (while the commit
   itself stays correct). Hit this early in the session, caught it by noticing `grep` for
   the new entry's own text came back empty post-restore, and fixed the working tree before
   it could compound. **Recurred a second time** later the same session, same root cause —
   caught the same way. The fix each time: rebuild the restore target from the CURRENT
   working file plus the same edit, not from a stale earlier copy.
2. **A Rule-8 near-miss.** A draft PUNCHLIST entry (the anomaly device-list bug) quoted a
   real device name and LAN IP as its worked example, pulled from investigating the actual
   live incident. Caught before committing, sanitized to placeholders — the technical point
   didn't need a real value to land it.

## The process gap worth naming on its own

Twice this session, an operator decision was described as "already taken" / "already
committed" by referencing a commit hash — and in both cases the hash pointed at the
**private handoff mirror** (`~/work/nemesis-internal`), not this public repo. The
pseudonymization decision (`c5f7a1c`) had never reached `PUNCHLIST.md` until Window 2 wrote
it this session, sourced from the private handoff's decision record and re-verified against
code first. A second, structurally identical case (a QUIC/nftables static-policy-table ADR
decision) appeared late in the session as uncommitted `PUNCHLIST.md` content from another
window, also describing itself as "already taken" — not yet reconciled by Window 2 as of
closeout. A private handoff commit and a public PUNCHLIST entry are two different artifacts;
this is worth a cross-window habit check rather than treating either instance as a one-off.
