## 1. DNS root cause CORRECTED — ADR 0002 superseded by ADR 0005

**The earlier DNS conclusion was wrong at the layer it blamed.** ADR 0002 pinned the
DNS failure on PIA's killswitch + policy routing (the *routing* layer). This session
proved the real mechanism is **client-refusal-by-source**: the test
`-b 127.0.0.1` (binding the query to the loopback source) reproduced the refusal
deterministically — the failure is in *which source address the client is allowed to
query from*, not in route/killswitch selection.

**Consequence:** the previously-considered DNS *guard* solves the **wrong layer** — it
would patch routing when the defect is source-based client refusal. So the guard is
shelved. **ADR 0002 is superseded by ADR 0005**, which reframes the whole area as a
firewall-engine / device-auth architecture (see §4).

**Workaround on this box until the firewall engine is built:** run **VPN-off** for
Claude Code connectivity. This is a stopgap, not a fix — the durable answer is the
firewall engine (ADR 0005). The read-only VPN watcher (outside the repo) corroborated
this: see §6.

## 4. Architecture captured this session (PARKED — ADR/roadmap-bound, mostly NOT built)

Captured per Rule 7. The headline is **ADR 0005**; the rest are roadmap docs.

- **ADR 0005 — firewall engine as a foundational primitive.** The firewall engine is not
  a feature, it's the **base primitive** everything else (DNS control, device auth, tamper
  response) builds on. Includes: **device auth Level 2**, **hardware binding**,
  **proportional tamper response**, and a **forward build sequence**. This is what
  supersedes ADR 0002's DNS framing — the DNS issue becomes one consumer of the engine,
  not its own subsystem. (`docs/architecture/0005-dns-firewall-device-auth-architecture.md`.)
- **Product thesis — built-in IT expertise.** The product *is* enterprise-grade
  zero-day/behavioral detection + whole-network security at non-enterprise pricing, with
  the expertise built in. (`docs/roadmap/product-thesis-built-in-it-expertise.md`.)
- **Market position — the remote / infrastructure-light / expertise-light edge.** The
  differentiated wedge is users who are remote, have little infrastructure, and little
  in-house IT expertise (see §5 — Starlink/remote-worker is the *core* market, not a niche).
- **Adaptive link-aware agent + clock sync.** The commercial agent must stay robust over
  bad links (Starlink/cellular): adapt cadence to link quality, and sync clocks so
  findings/tickets are correctly ordered across devices.
  (`docs/roadmap/adaptive-link-aware-agent-clock-sync.md`.)
- **Watcher productization** — generalize the throwaway VPN watcher into a toggleable
  connectivity self-diagnostic. (`docs/roadmap/diagnostics-connectivity-watcher-tool.md`.)
- **Tiered diagnostic reports** + **AI tool-aware diagnostic loop** (the AI knows which
  diagnostic tools it can invoke and chains them) + **reassurance/escalation routing**.
  (`docs/roadmap/diagnostic-scan-scope.md`, `diagnostics-ai-tool-aware-loop.md`,
  `diagnostics-ai-reassurance-escalation-routing.md`.)
- **DB resilience via backup-promotion** — recover a corrupt shared DB by promoting a
  verified backup.
- **Agent auto-load-by-ownership** — agents load capabilities based on device ownership
  context (ties to the §10 ownership/consent boundary from the prior supplement).
