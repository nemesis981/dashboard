## The lateral-movement/gateway-mode thread, in full

`gateway-mode-scoping.md` shipped this week, which resolved a build-status hold on
`lateral-movement-outbreak-detection.md` — but not the way anyone expected. Gateway Mode
shipping does not restore unicast peer-to-peer LAN visibility on a flat, unsegmented network
(this box's own topology): a switch delivers same-subnet unicast without consulting the
gateway, regardless of which device holds that role. This was corrected across every place the
roadmap doc had framed it as pending gateway mode, with the reduced-scope detection form
(broadcast/self-inclusion/egress signals) documented as the **permanent** shape for non-VLAN
installs, not a temporary compromise.

Naming then had to be finalized before Window 1's build could proceed. This window's first
proposed name ("Post-Detection Behavior Correlator") was substantively wrong — Window 1
correctly flagged that it only described one of two triggers (a managed device correlated
against a prior finding) and misdescribed the primary case (an unmanaged device's own
broadcast-visible behavior, which has no prior finding to correlate against). Settled: two
finding types (`post_detection_egress`, `lan_probe_scan`/`unmanaged_device_probe`), a new
module (`lan_behavior_monitor`) rather than widening `lan_integrity`'s charter — and that
module-placement call was explicitly re-derived from `lan_integrity`'s own stated founding
principles (scoped by class, not mechanism; a serving module must not judge its own
competitors) rather than assumed from convenience, per the operator's explicit instruction to
do so.

Window 1 built and deployed both finding types same day. Deployment was independently
verified (not just taken on the commit message's word) via `dashboard`'s
`ExecMainStartTimestamp` matching the final commit's timestamp, and all services active.

## The CLAUDE.md standing-practice addition

Operator-directed, confirmed **directly** (explicitly not via a peer's relay, even though a
peer had already characterized it as operator-directed) — the standing discipline of asking
for the operator's own direct word before touching CLAUDE.md held all day, including here.
New rule: when a roadmap item is picked up for build, its dependency/infrastructure claims
must be verified against actual code, not just its build-status header. The existing
"classify against code, not the header" discipline already worked and had caught drift on its
own — the gap this closes is that a file can be correctly classified while its *body* still
states a false premise about infrastructure it depends on. Two real incidents this week
(the `firewall.py` posture-mapping claim, and FLEET-auto's stale unbuilt claim) both escaped
the existing check for exactly this reason.

## The `net_identity.py` thread — how it ended, mid-flight

Window 1 shipped a consolidation of 3 duplicate "what are my own local addresses" call sites.
A cross-session message (relayed by the operator, framed as possibly-stale) asked this window
to confirm whether a broader "six-site" finding was genuinely new or already superseded. This
window did NOT take either the peer framing or the claim itself on faith — independently
verified the consolidation commit's actual scope (exactly 3 sites, matching what was
described) and independently confirmed the three additional sites genuinely contain their own
duplicate enumeration logic (grep-verified specific functions in each file) before relaying
anything. Sent directly to the correct peer session after resolving a stale window-identity
mapping the operator had given earlier (cross-checked via Claude-Session trailer, which had
been the reliable attribution method all day).

Window 1's response: independently re-verified all three sites itself (not taking the relay at
face value either) and found each is a genuinely different concern — different output shape,
different filter, or a different host/process entirely (the agent runs on client endpoints,
can't import appliance-side code) — not a missed consumer. Correctly declined to force-fit them
and is surfacing the full six-site picture to the operator for a scope decision rather than
deciding unilaterally. **This exchange is a good example of the project's own verification
discipline working as intended across two independent agents, each re-checking rather than
trusting the other's report** — worth noting as a positive pattern, not just a status update.

Separately, Window 1 flagged its VM test environment (the appliance-master clone) as
inaccessible for a service-level validation step, relying on an in-process equivalence proof
