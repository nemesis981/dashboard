### 3. WiFi-security design + build (Feature 6 / L1 / L2)
The evening's push. **Feature 6** (`a9ba84d`): an observation-only IP-reputation cache — the agent
pulls a dataset from the server and measures locally, never enforcing. **L1** (`cd009ca`): DNS
set/restore plumbing + kill switch, default OFF — deliberately NOT pointed at the tunnel Pi-hole
because **ADR 0005** (Pi-hole refuses tunnel-sourced queries) is unsolved; enabling it would exercise
plumbing only. **L2** (`a005ed0`): WinDivert reputation blocking on TCP handshake-initiation +
stall-watchdog, default OFF.

Mid-review we corrected the L2 scope framing: the filter `outbound and ip and tcp and tcp.Syn` matches
SYN **and SYN-ACK**, so it's **bidirectional** (blocks outbound-to-bad-IP *and* inbound-from-bad-IP).
This is **intentional** — outbound-only would be asymmetric protection for a security product. Fixed
the framing in roadmap docs (`d944703`) and in the code comments (`455c998`), and captured the accepted
tradeoff: during a hang, a *new inbound* connection is briefly blocked (~5s until the watchdog recovers);
established sessions are untouched.

### 4. L2 Step-5 validation (real evidence)
Ran the battery on the Windows test VM (pydivert 3.1.3 under the VM's **system Python**), harnesses
committed as `430a2fe`: `--test-normal` (traffic passes, filter active), `--simulate-crash` (per-packet
fail-open, reinjected), `--simulate-hang` (**watchdog fires at exactly 5.0s**, force-closes the handle,
traffic restored), and the kill switch (`sc stop WinDivert` parks at STOP_PENDING while the handle is
held → **taskkill is what frees it**; both together restore traffic). The inbound-during-hang probe
confirmed the SYN-ACK bidirectional behavior live: fresh inbound went UP→DOWN(~6-9s)→UP, established
survived.

### 5. 🔴 The pydivert discovery (biggest finding of the night)
Deploying the WiFi work, we tried to actually enable L2 on `build3-83` — and the frozen agent logged
**`L2 disabled: pydivert/WinDivert unavailable (No module named 'pydivert')`**. Root cause:
`build_installer.py` does `--collect-all pydivert`, but the **CI workflow never `pip install`ed
pydivert**, so PyInstaller had nothing to collect. **Consequence: L2 was inert (fail-open) in EVERY
agent ever shipped** — tonight's Step-5 tests validated the logic only because they ran the source
under system Python, not the frozen agent. Fixed by adding `pydivert` to the CI deps (`6b88ccb`);
rebuilt; **verified by direct contrast** — old build (`00125a79`) had `WinDivert64.sys`/`WinDivert.dll`/
`pydivert` all absent, new build (`1c8b8269`, provenance `49061c5`) has all three present in the frozen
exe. This is the kind of gap that only surfaces when you test the *packaged* artifact, not just the code.
