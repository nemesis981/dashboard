## 4. Afternoon: zero-day / TLS / business-model design capture (capture-only, no code)
A full design session on the L3 zero-day architecture, TLS interception, and the business/
resource model. Four commits, each Rule-8 scanned before commit:

**a. ADR 0009 addendum** (`1285a33`, appended to `docs/architecture/0009-security-inspection-proxy.md`):
- **Origin-based WiFi routing** — WiFi-origin traffic is ALWAYS a tunnel-pipeline candidate
  regardless of destination; wired-origin traffic is already covered by the existing LAN-tap
  Suricata capture and never needs the tunnel. This replaces destination-based reasoning and
  removes the topology-dependency Fork B's original selection model had (Fork B's Piece 1
  selected on reputation verdict alone, with no origin check).
- **Two-layer model**: (a) continuous, lightweight, server-side rule-based behavioral/pattern
  scoring as the TRIGGER (same shape as the existing lateral-movement risk-weight table — open
  question whether it's literally reused or a parallel engine); (b) tunnel-routed Suricata
  payload inspection as the CATCH, invoked on unknown reputation (Fork B's original trigger) OR
  a behavioral escalation on a previously-cached-clean destination/pattern.
- **Hard principle**: the agent is a telemetry sensor and enforcement point ONLY — it never
  performs pattern-matching, scoring, or classification judgment locally; all detection
  judgment is server-side. Stated as a hard product requirement (preserves the self-hosted-
  central-server value proposition), not a cost-driven preference.
- **Dynamic cache**: replaces the static TTL-only reputation cache — a behavioral signal can
  invalidate a cached-clean entry, not just time expiry. Named, accepted limitation: an
  in-flight connection can't be cleanly converted to inspected mid-stream (mirrors Fork B's
  Piece 5 in reverse); the realistic mechanism is invalidate-going-forward (next connection to
  that destination/pattern gets inspected) + alert-the-current-connection via the existing
  pipeline, even though it may complete uninspected.
- **Shared fleet intelligence**: server aggregates telemetry across all enrolled devices,
  classifies, and pushes verdicts back to the whole fleet — detection stays 100% server-side.
  Flagged (not resolved) likely overlap with `community-signal-dedup.md` and
  `open-source-threat-feeds.md` — those operate at community/global scope, this at
  single-customer-fleet scope; don't build three parallel aggregation systems.
- Status: direction decided, NOT built. Supersedes/refines `adr-0009-l3-fork-b-scope.md`'s
  selection criteria; that doc's Piece 1–5 transport mechanics still apply underneath.

**c. New scoping doc — TLS interception + sterilization** (`1d6d2d2`,
`docs/roadmap/tls-interception-sterilization-scope.md`): the decision to build full TLS
interception (decrypt-inspect-reencrypt) for genuine HTTPS payload coverage. Sterilization
policy: plaintext inspected transiently (in-memory) only for clean traffic; bounded evidence
(rule ID, hash, possibly redacted excerpt) retained on an actual detection — exact threshold
named as a real open policy decision. Toggle: home default = strict sterilization; business/
commercial can opt in to fuller visibility over their own equipment. Three named hard unknowns,
none resolved: (a) CA trust distribution with no MDM, (b) certificate-pinned apps need an
explicit bypass/allowlist, (c) resource tension between full decryption and the existing
low-footprint selective-inspection design. No session estimate, same TBD treatment as (b).

**d. Business model + resource-analysis module** (`946d7b4`):
- **Tier structure**: free = home use, full uniform detection depth, never stripped down;
  commercial = FLAT price, not device-count or network-size based; hardware/bandwidth is
  customer-owned infra cost, explicitly outside Nemesis's pricing model.
- **Locked principle**: detection/security capability is uniform at every tier and scale — only
  admin/organizational features (multi-user, roles, MSP cross-site, device caps) differ by
  tier. Security is never the upsell.
- **Resource philosophy**: minimize server cost relative to network size and keep per-device
  agent cost very low as explicit engineering targets; accept some hardware/bandwidth growth as
  a fair, expected, transparently-communicated cost of scale — not something to hide or
  architect around at all costs. Named tension with the TLS resource-tension unknown (4c above).
- **AI-strictly-optional principle**: AI is never part of the detection/scoring/decision path.
  Confirmed uses only: (1) opt-in post-detection explanation, (2) opt-in narration for the new
  resource-scaling advisor's recommendations. All core detection/scoring/resource-measurement is
  deterministic, local, zero external AI dependency.
- **Product thesis**: "enterprise-level protection for all user levels" — AI as the enabler that
  lets a small team price this at a fraction of an enterprise SOC relationship, without reducing
  detection depth for smaller customers.
- Captured in `product-thesis-built-in-it-expertise.md` (expanded — Step 0 of that session found
  adjacent-but-non-overlapping content there, so this extends rather than duplicates it).
- New `docs/roadmap/network-resource-scaling-advisor.md` for the resource-analysis module itself
  (deterministic local measurement, hardware/bandwidth/cloud-resize recommendations, optional AI
  narration, covers both physical and cloud deployments) — deliberately a **new file**, not
  folded into `nemesis-overhead-meter.md` (that file is Nemesis's own self-overhead/leak-
  detection diagnostic, a genuinely different concept; the distinction is flagged in both files
