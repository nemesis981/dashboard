## Arc of the day

Started with the morning migration-status audit (found and fixed a real gap:
`dashboard.service`'s deliberate hardening exception wasn't codified in `gen_units.py`,
so a future regen could have silently hardened it and broken `sudo -n ufw`). From there
the day covered five separate threads, roughly in this order:

1. **CSRF fix** on three quarantine/action routes (GET→POST), done urgently and directly
   by Window 2 (user-authorized deviation from the normal split) because Window 1 was
   blocked waiting on it to rebase the ufw-helper rewire onto.
2. **The ufw helper (`nemesis_fwd.py`)** — a privileged process with three independent
   verification layers (kernel-verified peer identity via `SO_PEERCRED`, a users-table
   admin-account lookup, a bcrypt credential check), plus its deploy tooling and,
   later in the day, tiered account lockout matching `dashboard.py`'s own scheme.
3. **Design/roadmap capture** — ADR 0018 (attacker-resistant backup + manifest-based
   recovery) and a roadmap stub for three future Windows-agent requirements tied to the
   paused memory-injection module.
4. **Data Manager v1.1** — explicit table lists, three-state enforcement modes, and
   column-level grants retrofitted onto the ADR 0006 gatekeeper.
5. **The core_module layout move** — six daemons (alert_watcher, hw_monitor,
   device_scanner, watchdog, malware_canary, diagnostics_watcher) relocated from
   `alert_manager/` into their own `core_module/<name>/` directories, via a careful
   copy-then-delete two-commit strategy (Commit A additive, Commit B removes the old
   copy only after the new one is proven live). This consumed the second half of the day.

Two private audits were run alongside this (kept out of the public repo per Rule 10 —
they'd read as an attack roadmap): dashboard's sensitive-action surfaces mapped against
the three-layer-verified pattern being built for the ufw helper, and the core_module
identity/DB-access landscape ahead of the layout move. Both live in

## Bugs found and held this session (the review discipline paying for itself)

Every one of these was found during independent verification, not trusted from a
handoff claim — each was held, sent back, fixed by Window 1, and re-verified by direct
reproduction before landing:

- **`GuardedConnection.executescript()` NameError** (`sql` vs `stmt` — a copy/paste slip)
  in the Data Manager retrofit. Reproduced directly, fixed, re-verified by reverting →
  confirming the new regression test failed with the exact predicted error → restoring.
- **Missing test coverage** for the same retrofit — Window 1 added four new test
  sections; ran the real suite and got a genuine `ALL PASS`, not a re-read of a claim.
- **`migrate_core_module.sh`'s `--verify` silent-abort bug** — `set -euo pipefail` +
  a `journalctl | grep | tail | sed` pipeline that can exit 1 on no-match, called as a
  bare statement in a loop with no guard. Reproduced with a mocked systemctl/journalctl
  harness and `bash -x`, confirmed the exact abort point; Window 1's `|| true` fix
  re-verified across all four state combinations.
- **`install.sh`'s core_module blind spot** — `deploy_services()` had zero awareness of
  the new per-process directory layout, meaning a fresh install would silently deploy
  stale `alert_manager/*.service` units (or, worse, a unit pointing at a file Commit B
  had already removed). Found during Window 2's own pre-action check before attempting
  Commit B, not flagged by Window 1 — sent back, fixed (`core_module/*/` globbed in
  first), re-verified against the real 8-service search order.
- **Two live consumers of the old `alert_watcher.py` path**, found during Commit B
  review despite a handoff claim that nothing imported it: `test_quarantine.py`'s
  `sys.path` only covers `alert_manager/`, and `deploy_nemesis_fwd.sh`'s
  `check_sources()` hardcodes the old path. `alert_watcher.py`'s Commit B is held on
  these two fixes landing; the other four (device_scanner, watchdog, malware_canary,
  diagnostics_watcher) had no such consumers and were removed today.
