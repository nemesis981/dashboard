## Part 1 — ADR 0006 v1: closing the loader-enforcement gap
The morning's ADR 0006 status fix (see supplement 002) had explicitly flagged one gap against
the ADR's own v1 definition: `modules_loader.py` didn't check anything, so Data Manager
compliance was voluntary-by-migration, not loader-guaranteed. Window 1 closed that gap this
session with a real, verified implementation:

- **`_check_data_manager_contract()`** — an AST-based static check, run before any module code
  executes, that refuses to load a module importing raw `sqlite3` or the bare `get_db` accessor.
  Raises a structured `ModuleEnforcementError` naming the module, the violation, and the line.
- **Verified, not assumed**, before any docs were written: simulated the check against all 7
  real modules (the 6 migrated DB-users + newly-discovered DB-free `dhcp`) — all pass. Simulated
  5 synthetic violation cases — all correctly refused.
- Docs updated to match across three files in one commit: ADR 0006 (status, enforcement section,
  build sequence, architecture diagram all corrected), the ADR-status audit (row amended in
  place, flagged as a same-day post-audit change), and CLAUDE.md (a new standing rule added
  alongside the Window 1/2 split and push-coordination; the old Tier-2 section trimmed to avoid
  duplicating it, but kept the actor-mechanism-unwired finding since ADR 0006 itself doesn't
  call that out).
- **ADR 0006 has no remaining gaps.** v2 (schema gatekeeper) is on record as explicitly
  *deferred* — waiting for the L3 work below to produce real schemas to design against — not
  merely unstarted.

## Part 2 — L3 three-tier consolidation
The operator brought a consolidated design-capture document (originally referenced at a
`/mnt/user-data/outputs/` path that doesn't exist on this machine — a different environment's
path; the operator pasted the content directly once that was flagged rather than having it
guessed at). The document organizes a full day's L3 design discussion into three tiers:

- **Tier 1 — mirror/passive (default, always on)**: this is what the existing ADR 0009 addendum
  already described (origin-based routing, the trigger/catch model, the sensor-only principle,
  the dynamic cache, shared fleet intelligence) — now explicitly named as Tier 1's detail rather
  than restated.
- **Tier 2 — full inline inspection (toggle, off by default)**: the TLS interception work,
  extended today with the full "undetectable inline" design — side-channel normalization,
  cache design keyed on cert fingerprint (not hostname), dual randomization, evasion-probing
  handling, pinned-app allowlisting. Framed honestly throughout as an R&D goal industry-wide,
  not a guaranteed property.
- **Tier 3 — client-side late triggers (always on, narrow)**: brand new. A short, enumerated
  list of local agent actions (shadow-copy-deletion attempt, canary-file touch, mass
  file-operation pattern) that fire in milliseconds without a server round-trip, because
  ransomware's damage window closes faster than a server verdict can return.

**The one real finding worth flagging on its own:** the source document repeatedly attributed
the sensor-only principle, and Tier 3's conflict with it, to "ADR 0011." That's wrong — ADR 0011
is the Enrollment Security Model (tokens, TOFU, review cards) and has no sensor-only language
anywhere in it. Grepped the repo to confirm the actual principle lives in the ADR 0009 addendum
(written earlier this session). Rather than writing Tier 3's exception into the wrong ADR, every
amendment was redirected to ADR 0009's addendum, and the mis-numbering is called out explicitly
in the new Tier 3 doc so a future reader doesn't repeat it. **Reported this to the operator
before committing; confirmed the redirect matched intent.**

### Decisions made
- Resolved (not left open, per explicit instruction): the Tier 3 vs. sensor-only conflict.
  Default/floor case (Tier 2/3 off) is unchanged — pure sensor. Tier 3 ON adds a narrow,
  auditable exception: unilateral local action ONLY on the enumerated trigger list, nothing
  else ever judged locally. The reasoning (server round-trip too slow for ransomware's
  shadow-copy/mass-encryption window) is stated plainly, not just the rule.
- Left open, per explicit instruction, as inline TBD notes rather than blocking gates: whether
  the mass-file-operation trigger ships (higher false-positive rate than the other two
  candidates), and the evasion-probing-vs-cert-pinning-failure disambiguation problem. Both are
  written as "decided during build/testing," at the specific point in the doc where they arise
  — not as a separate open-questions list to resolve before code starts.
- Organizational choice: extended the existing `tls-interception-sterilization-scope.md` with
  the undetectable-inline design (Pieces D–I) rather than creating a separate doc — it's
  squarely about how to do Tier 2 undetectably, the same topic that doc already scopes, and
  matches how the other companion docs are organized (one doc per major topic, not one per
  design session).
- Created a new companion doc for Tier 3 (`adr-0009-l3-tier3-local-triggers-scope.md`) rather
  than extending ADR 0009 itself with the full trigger-list detail — matches the existing
  pattern where the ADR addendum stays a summary/decision record and companion docs under
  `docs/roadmap/` hold the full working detail.
