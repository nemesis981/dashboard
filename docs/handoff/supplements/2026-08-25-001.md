`iptables` DROP idempotency fix, a pure traversal-simulator module that determines whether a
packet actually reaches the DROP (not merely whether the rule exists — the failure mode

## CLAUDE.md: shared-tree attribution rule (`2fcf77c`, corrected `8ad5cd1`)

Window 1 drafted this after a real near-miss in `~/work/nemesis-internal`: a commit's parent
was another window's commit that had never been pulled — one shared checkout, three windows
writing to it. The draft's proposed mechanism (`git log --format='%h %an %s'`, using `%an`
to identify whose commit is whose) was checked before landing and found broken: every
window commits under the identical shared git identity, so `%an` cannot distinguish them.
Corrected in a second commit rather than amended, per this session's own standing git
discipline (new commits, not amends, unless explicitly requested) — dropped `%an` entirely,
replaced the primary signal with this repo's real commit-subject naming convention
(`handoff(windowN): ...` self-identifies; feature-area prefixes narrow by known ownership),
kept session-SHA recognition as a secondary signal, kept `git reflog` (unaffected by the
identity problem, since it reads ref history not authorship).

## CSRF batch + auto_approve schema fix (`e116188`, `3ef5a1d`, `6f3ebe6`)

Window 1's fix for six GET routes that performed a write, a spend, or an outbound call while
answering GET — the sharpest was `report_abuse`, where an `<img>` tag on any page an
operator visited could file a permanent third-party AbuseIPDB report under default
SameSite=Lax cookies. Converted to POST + `request.is_json` guard (the same two-layer
pattern already established by `api_ram_recovery_clean`). `roles.py`'s four `(_U, _A)` pairs
were correctly left at `(_U, _U)` rather than promoted, since the method conversion alone
would have silently locked plain users out of diagnostics they'd always been able to run —
one variable, not two.

Independently re-verified by Window 3 before I committed: every bare-GET route AST-scanned
to confirm six was the right count (two false leads examined and correctly dismissed —
`scan_page`'s DELETE match was inside a rendered JS string, and `install_windows_zip`'s bare
GET write is not CSRF-shaped since the URL token is itself the credential, not a session
cookie). I re-ran both suites myself before committing (158/0, 10/0), reviewed the actual
diffs line by line rather than trusting either window's account, and confirmed none of the
six routes had a stale caller left in JS.

`auto_approve`'s schema default was corrected 1→0, since a default that fails open on a
security decision is backwards regardless of who currently relies on it. **Explicitly not
described as a production fix in the commit message**, per the operator's specific
instruction: SQLite cannot ALTER a column default, so the live database keeps `DEFAULT 1`
in its stored schema — verified directly against the running `/var/lib/nemesis/alerts.db`,
not inferred. Production stays safe today only because the single writer already binds the
column explicitly on every insert, which this commit doesn't touch or establish.
