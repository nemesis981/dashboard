## Three review-caught bugs, each held and re-verified before landing

Every one of these was caught during review, not shipped and found later — each held the
commit, sent a precise bug report back, and re-verified the fix independently (diffed against
the exact flagged version, re-ran the full gate, and in one case directly reproduced the
failure) rather than trusting the "fixed" claim.

1. **`migrate_to_opt.sh --verify`, run standalone, false-failed after a successful migration.**
   `detect_src()` searches `/opt/nemesis` first, so it returned the NEW tree as `SRC`, and
   `do_verify` then asserted the new tree was "the old tree still present." The `--run` path
   never hit this (it retains the correct `SRC` from `preflight`), which is why the VM test
   cycle missed it. Fixed via a `resolve_verify_src()` that reads the true pre-migration path
   from the migration-time stamp file.
2. **Four systemd units silently lost real ordering dependencies on regeneration.**
   `gen_units.py`'s first pass modelled `After=` as a single string with no `Wants=` field at
   all — alert-watcher lost its `suricata.service` ordering (it tails a log Suricata creates),
   vpn-dns-guard lost its `pihole-FTL.service` ordering plus an `EnvironmentFile`, watchdog lost
   the same `EnvironmentFile`, and device-scanner's `After=` silently changed target. None of
   the mechanical gates catch this class of loss — a unit missing a dependency is still
   perfectly valid syntax. Fixed by making `after`/`wants` explicit lists carried over verbatim,
   verified directive-by-directive against `git HEAD` for all 8 services, plus a new
   `gen_units.py --check` mode (tested both directions) so this can't silently recur.
3. **`migrate_to_opt.sh --rollback`'s stale-unit warning pointed at a snapshot path nothing
   created.** The detection was correct (units left pointing at `/opt/nemesis` after rollback);
   the suggested fix command, `<snapshot>/units-before/*.service`, wasn't backed by any real
   backup step anywhere. Fixed by having `install.sh` actually back up existing units to
   `/var/backups/nemesis/units-<timestamp>/` before overwriting them, with the warning falling
   back to git-reconstruction instructions when no backup exists. The fix also included a
   `set -euo pipefail` interaction bug (a bare `ls` on a non-matching glob aborting the script
   mid-warning) — reproduced both the failure and the fix directly in an isolated test rather
   than trusting the explanation.

## THE INCIDENT (2026-07-27, ~25 minutes of degraded production)

The operator ran `scripts/migrate_to_opt.sh --run` for real. Code and DB moved cleanly
(integrity confirmed), but the migration script does not deploy unit files — `install.sh`
does — so all 8 deployed units still pointed at the now-deleted `/home/<user>/dashboard`.
`do_migrate` restarts every service at the end of its run; with stale units, that drove all 8
into crash loops (`dashboard` hit `StartLimitBurst` and latched `failed`; the other 7 hit
`INVALIDARGUMENT`/"can't open file", restart counters at 23+). Window 1 had always deployed
units by hand immediately after migrating on the VM, so the operator's actual sequence — run
the migration script alone — was never exercised before tonight.

Recovered forward, one service at a time, verifying each. **Independently re-confirmed, not
just relayed:** `systemctl show` on all 8 services right now reports `active`/`running`/
`NRestarts=0` with correct `/opt/nemesis` `ExecStart` paths and correct per-service `User=`.

Two structural gaps this exposed, now tracked as open items: `migrate_to_opt.sh` will let
anyone re-run this exact sequence and hit the same incident (it must either deploy units itself
or refuse to restart services when installed units reference the old path); and `--verify`
still doesn't check that units point at the new location at all (only code location, DB
location, and old-path-gone) — a materially different gap from the standalone-`--verify` bug
fixed earlier in the day.

All 8 verified `active`/`running`/`NRestarts=0` directly via `systemctl show`, not relayed.
`systemd-analyze` exposure: 9.6 UNSAFE → 2.0 OK for the six de-privileged services;
device-scanner 2.2 (retains `CAP_NET_RAW`); dashboard unchanged at 9.2 UNSAFE, deliberately.
UIDs for the six confirmed directly via `id`: 985/990/991/992/993/994, all `gid=972
(nemesis-db)`.

**Dashboard is deliberately not hardened.** It elevates via `sudo -n` in ~10 places, including
`alert_manager/firewall.py` (the ADR-0005 ufw chokepoint). `NoNewPrivileges=yes` makes the
kernel ignore setuid, so `sudo` cannot elevate under it — proven by Window 1, not assumed:
`sudo -n ufw status` succeeds normally, fails with "the 'no new privileges' flag is set" under
`--no-new-privs`. A hardened dashboard would have started, looked healthy, and been unable to
block or quarantine anything — a silent loss of a core security function. The unit carries an
in-file comment explaining this and warning against adding hardening before the code changes
land. Confirmed working after recovery: `firewall._run_ufw('status')` → rc=0; `load_blocked_ips()`
succeeded.

Two things I could not independently verify from this session (no passwordless sudo here):
attestation journal lines for the six services (the underlying UID/capability facts are
confirmed via `id`, but I couldn't read the journal itself), and the live `/etc/sudoers.d/`
listing (cross-checked instead against the 18:46 pre-migration USB snapshot, which only
partially corroborates — see Open Items).

## Deferred assessments (live only in conversation — not yet durable)

- **PostgreSQL migration — deferred.** Measured SQLite/WAL on this hardware: 18,126 writes/s
  single-writer, 25,619 w/s across 16 concurrent processes, zero lock errors, against a
  worst-case venue projection of 1,000 w/s (~25x headroom). The throughput case for migrating
  didn't survive measurement. The remaining case is role-level enforcement and multi-tenancy,
  not speed.
- **Dedicated-writer-process architecture — deferred.** Measured Unix-socket IPC at 62,666
  w/s, faster than today's connect-per-write pattern. Viable, but superseded by the
  de-privileging work that shipped instead.

Flagging only — if these should be durable, they need a roadmap stub or an ADR. Not decided
tonight.
