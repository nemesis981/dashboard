## ADR 0004 Stage 1 — the signed-task channel, all four steps shipped same day

Built incrementally through the day by Window 1, reviewed/committed/pushed by Window 2
after independent verification at each step (never just trusting an embedded suite's
self-reported pass):

- **Step 1** (`00c087f`) — server signing keypair + trust-anchor delivery. Deliberately
  changes no runtime behavior; establishes the plumbing (keypair generated once on
  `hw_monitor` startup, privilege split real not decorative, anchor delivered out-of-band
  via the token-gated installer download) the next three steps depend on.
- **Step 2** (`75b789e`) — signed task envelopes with fail-closed verification.
  `device_id` inside the signed material (prevents cross-device replay of a captured
  envelope); the same canonicalization rule heartbeat signing already uses, reused rather
  than duplicated, because a second near-identical canonicalization is exactly the kind of
  defect that passes in testing and fails invisibly in the field.
- **Step 3** (`d4cd2a7`) — task dispatch via the heartbeat response, replay protection
  rebuilt on `os.open(O_CREAT|O_EXCL)` per-task marker files (portable to the Windows
  agent, unlike flock/fcntl) instead of the old read-check-write JSON store. **Independently
  re-verified beyond the embedded suite**, per Window 2's request: reconstructed the OLD
  store and ran 16 real separate *processes* (not threads) racing to claim the same
  task_id against both implementations. Old store: 16/16 would have executed the replay.
  New store: 1/16 won. This is the standing "verification code must prove its own premise"
  practice applied to a concurrency fix specifically — a threading-only test would not have
  caught this, since the real threat model here is multiple agent processes.
- **Step 4** (`b2f5e6a`) — task results, rules-content digest, server key rotation.
  **This is where the day's one genuine process incident happened** — see the dedicated
  section below.

**Terminology trap, flagged explicitly for whoever picks this up next**: "Stage 1 Step 4"
above is a different thing from ADR 0004's own original "Step 4" (Scheduler/Execution/
Reporting + `scan_threats`→`malware_findings` migration + fleet-wide distribution), which
remains unbuilt. `8323913` corrected the ADR doc's stale status line mid-day, before Stage
1 step 4 itself landed — worth rereading that commit's message if the numbering seems to
contradict itself later.

### The Step 4 incident: an abandoned 3-way commit split, and what it caught

Window 1 originally handed off Step 4 with precise line-range citations for splitting
`agent.py` and `hw_monitor.py` into three separate commits (result-reporting / rules-digest
/ rotation), matching the granularity of Steps 1–3. Window 2 built the split using
`difflib.SequenceMatcher.get_opcodes()` (authoritative diff mapping, not manual line
counting) and cross-validated against Window 1's citations — close, but isolating a
Commit-A-only working tree and running its test suite produced a **real `NameError`**, not
a false alarm. Root cause: a `try/if ROTATE_ACTION/else/.../record_result()` block in
`agent.py`'s `_handle_response_tasks` was genuinely interleaved at a granularity finer than
any line-range citation can express — the success-path `record_result()` call (Part A)
depended on an `err` computation that Window 1's citation had bundled into what looked like
a wholly-Part-C block, and the same shape recurred for the failure-path call.

Operator called a halt: confirm clear of the three files, hold everything until Window 1
recovers. Window 2 restored all three files to their exact pre-analysis state (verified
byte-identical via `diff -q` against pre-swap snapshots) and confirmed nothing had ever
been staged or committed. Window 1 recovered, re-verified 16 suites/468 checks, and
reissued instructions to commit Step 4 as **one** commit — confirmed genuinely
non-separable given the interleaving found. Window 2 independently re-verified before
committing (213 checks across 5 suites, all against the real frozen tree — not the "468/468"
claim taken on faith), caught and corrected a second issue (the staged `PUNCHLIST.md`
carried 5 entries when only 1 belonged to this commit — see next paragraph), and committed/
pushed `b2f5e6a`.

**Note for the record, not a defect**: landing Step 4 as one large commit after three small
precise ones is a visible discontinuity in the day's commit-granularity pattern. This is a
genuine property of the source (real interleaving across three logical features inside
single functions), confirmed by direct investigation, not a process slip.

## Storage/retention build — 5 pieces, all live

Full detail: `HANDOFF.md` §1 and §3. Two design decisions worth preserving beyond the
commit messages themselves:

- **No automatic permanent deletion, ever** (`ef65155`) — an explicit operator decision.
  Archival (move to a file, leave a reference, nothing destroyed) is fine and automatic;
  permanently discarding data must be a user-initiated action.
- **A derived summary is not a copy.** This caught the originally-approved `dm_operation_log`
  retention design (summarize-then-delete) before it became code — min/max/avg cannot
  reconstruct the rows they came from, so the approved plan would have permanently destroyed
  audit-trail detail automatically while reading as ordinary retention. Redesigned to
  archive-then-coalesce (`3066205`) before any code shipped against the original plan.

Both `top_processes` archival (`97175ba`) and the `dm_operation_log` coalesce (`3066205`)
were verified against `.backup` copies of the live database with the same shape: row counts
identical before/after, content compared field-by-field (not just row count) between the
archive and what was cleared, three deliberately-injected failure modes each proven to
abort with live data provably unchanged, and a dry run confirmed to change nothing.

Archive/verify helper logic was duplicated between the two pieces at first (piece 4 was
already deployed against live data by the time piece 5 landed, so refactoring mid-build was
judged unnecessary regression risk) — filed (`3615cb4`, `17d1044`, `7a854fd`) and then
consolidated onto the Data Manager (`dd788ac`) once both pieces were confirmed stable,
scoped tightly to exactly the one duplication per explicit operator constraint.

## Concurrency-race emergency — found and fixed same day

Full detail: `HANDOFF.md` §1. Escalated to top priority mid-session after an audit of every
Data Manager caller found 38 read-then-act/file-collision sites and zero application-level
locking anywhere in the product — not hypothetical, the documented "4 canaries produced 204
tickets" incident from an earlier session is this exact bug class.

Two primitives shipped first (`a9f3472`: `transaction()` for BEGIN IMMEDIATE serialization,
`job_lock()` for whole-job flock exclusion including non-DB side effects), then all 10 HIGH
findings fixed same day. **Notably, `transaction()` itself was used in none of the actual
fixes** — every real fix wanted a structural answer instead (compare-and-swap UPSERT,
`NOT EXISTS`-guarded insert, or `job_lock`), because several of the races involved an SMTP
send, a billed Claude API call, or a tar.gz write in the critical section, and holding a DB
write lock across any of those would have stalled every other writer. Building the
primitive did not make it automatically the right tool for every finding — worth remembering
next time a "just wrap it in a transaction" fix is proposed for something with a non-DB side
effect.

One flagged HIGH finding (1.6, `anomaly_incidents` read-modify-write) was independently
re-verified as a **false positive** rather than fixed — its one real caller already runs
downstream of an `ON CONFLICT DO NOTHING` claim that serializes it. The audit had
contradicted itself, listing the enclosing region as already race-safe in its own table
while separately flagging the function it protects. Recorded explicitly: **the audit's HIGH
rankings need call-graph verification, not trust by default** — the same standing
skepticism this session applies to every other "done" claim, turned on the audit's own
output.

Every fix carries a control proving the *old* code actually failed, not just that the new
code passes — see `HANDOFF.md` §1 for the specific before/after numbers per finding. The
auth-throttle fix (`0e5b025`) is the one with real security weight: 10 concurrent failed
logins should trip the lockout counter to 10 and tripped it to 1, meaning an attacker making
parallel login attempts got free tries against exactly the control meant to stop that.

## Smaller findings and fixes threaded through the day

- Two more `keyprotect`-adjacent bugs caught live before shipping: a Windows dialog that
  could hang the agent forever because its `Toplevel` was parented to a withdrawn root
  (`896a1f6`, confirmed on a real frozen build — "there is no tkinter on this build host,
  which is exactly why the original bug survived 199 previously-passing checks"), and a
  frozen agent's log path resolving inside PyInstaller's ephemeral `_MEIPASS` extraction
  directory, gone the moment the process exits (`58b75bc`, filed not fixed).
- Installer provenance-on-Retry (`edc6133`) — confirmed live: retrying a failed install
  after Tailscale had already been installed on attempt 1 caused attempt 2 to record
  Tailscale as the user's own pre-existing software, meaning uninstall would leave it (and a
  live tailnet node) behind permanently. Fixed for the retry case with a per-process cache;
  the deeper fix (record provenance incrementally at install time) is one of the four held
  PUNCHLIST entries, not built.
- `is_private`-branching test trap (`dd4a1af`): RFC 5737 test addresses — this project's own
  prescribed test-data convention — are classified `is_private=True` by Python, so any code
  branching on address privacy silently skips them. Found while verifying the enrichment
  single-flight fix, when "0 of 8 callers got a result" didn't match what a working fix
  should look like. Fixed with a new `TEST_IP_PUBLIC` convention; CLAUDE.md Rule 11 updated
  with the caveat (`89b4807`) so it isn't rediscovered.
- Diagnostics false-positive chain: the connectivity watcher had been reporting DEGRADED
  continuously for 60+ hours from an IPv6-leak-protection false positive (`9b71d80`) —
  masking a real 23.1-hour total DNS resolution failure that happened inside that same
  stuck-DEGRADED window (`d868810`). The cross-reference is the actual point of filing both:
  fixing the false positive isn't cosmetic, it's what makes findings like the real outage
  visible at all. Neither fix is built yet — both filed as findings with a suggested
  direction. A roadmap stub (`0e1e479`) followed, proposing retention of diagnostics verdict
  *transitions* beyond the 48h sample cap, since both incidents above hit that cap during
  investigation.
- PIA VPN breaks tailnet agent enrollment (`95cc063`) — root-caused directly (PIA's policy
  routing blocks the tailnet CGNAT range even with `allowlan` on; three separate diagnostic
  instruments — `tailscale ping`, nginx logs, ufw logs — each falsely suggested otherwise).
  One claim in the original filing (a sustained post-disconnect IPv6 outage) was
  re-investigated and corrected two commits later (`fc1772a`) after the data didn't support
  it — recorded as a correction, not silently amended.
- PL-10's stale-text half is **re-closed** (`8c427e2`): the 08-02 reopening was a misreading
  — the tested build genuinely had no preauth key, and the "stale-looking" copy was correct
  behavior for that exact input. Resolved with the full closed→reopened→re-closed history
  preserved in the commit, specifically so a third reopening doesn't repeat the same
  false-positive read.
- `test_quarantine.py`'s arity drift, traced to the 08-02 core_module relocation and scoped
  to all three affected call sites (`8a1c909`, `37a405e`) — filed, not fixed.
- CLAUDE.md's code-window evening-handoff rule was added, then revised twice same day: first
